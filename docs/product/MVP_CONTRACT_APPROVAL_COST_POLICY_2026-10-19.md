## 1. 첫 계약 범위와 사람별 권한

- **첫 전문 역할:** requirements_auditor_v1 / 기획 검수 AI 권고; 소속 프로젝트 1개, 선택한 문서/고정 digest만 검사, 문서 읽기 전용 R0 도구 read_project_documents 1개, 신규 비공개 감사 보고서 R1 산출물 1종.
- **범위 외:** 원고 덮어쓰기·기존 업무 수정·코드 변경 등 R2, 외부 메일·배포·결제·병합·삭제·외부 공유 등 R3은 첫 MVP에서 차단. 모델 텍스트가 요청해도 실행 불가.
- **계약 조건:** 프로젝트/owner/역할/허용 도구/자료 범위·원본 버전/목적/시작·만료/통화/작업·계약 전체 한도/공급자 데이터 처리 고지 및 명시 동의 스냅샷을 고정한다.
- **owner:** 계약 승인·중단, 예산/계획/실행 승인, 보고서 수락·반려/수정 요청. **editor:** 문서 편집/계획 초안 제안 가능, MVP 첫 실행·청구·최종 수락은 불가. **viewer/outsider:** 계약/실행/원가/비공개 보고서 접근은 기본 불가(기존 프로젝트 문서 읽기 권한과 별도).
- **계약 UI 의존성:** Phase 2~3은 내부 테스트 owner 동의·서버 최소 계약 기록·R0 도구로 실증하며, Phase 5에서 고객용 역할 탐색/면담/계약 UX 공개. 내부 테스트 계약이 고객의 동의나 상용 결제를 대리하지 않는다.

## 2. 비용 발생 순서를 포함한 정상 실행 (TF-10~24와 정합)

1. owner가 기존 프로젝트의 2개 이상 문서를 선택해 범위/예상 비용/상한/공급자 전송·보존 안내를 검토. 이 단계는 **비모델 결정적 처리만 가능**, 비용 발생 모델 호출 금지.
2. **초기 계약 동의·활성화가 먼저다.** owner가 역할·원본·허용 도구/목적·데이터/비용 조건·상한·만료를 명시 수락; 서버가 actor/terms 버전·digest를 기록. 계약·전송 고지/동의 없이는 유료 AI PM 계획 생성도 차단.
3. PM 계획이 모델 생성이라면 **초기 계약에서 명시 승인된 PM 계획 비용 상한**을 원자적으로 예약한 뒤 서버 job으로 생성. 모델 미구현이면 사용자가 입력/수정한 **무과금 사람 계획 초안**만 생성하며 AI가 작성했다고 표기하지 않는다.
4. owner는 계획 버전·검사 작업 1개·입력 문서 digest·도구·예상 실행원가/승인 한도·수용기준을 검토하고 **계획을 별도로 승인**한다. 계획 미승인 상태에서 전문 AI 큐 진입 금지.
5. 작업 실행 요청은 owner/프로젝트·계약/버전·문서 소속/권한·예산·allowlist·승인을 검사하고 **멱등 요청 ID + 예산 예약 + run 생성 + 아웃박스**를 하나의 트랜잭션으로 수행해야 한다(현재 미구현).
6. 워커는 실도구/모델 호출 직전에 멤버십/계약/계획/문서 snapshot/예산·승인 만료·kill switch를 재확인. 실제 읽은 문서 ID/버전/digest를 run에 연결한다. 동일 프로젝트 밖으로 접근 불가.
7. 모델 생성 결과는 schema/출처/인용 위치/권한/범위를 서버가 검사. 자동 검증 PASS 후 **비공개 미수락 보고서**를 저장; owner가 수락·수정 요청·반려를 명시 결정한다.
8. **비용 정산은 사용자 산출물 수락과 독립**이다. 이미 발생한 공급자 원가는 실패/반려에서도 발생 가능; 고객 청구·환불은 별도로 최종 승인된 약관에 따라 처리한다.

**순서 결함 해결:** 10/19 최초 전문 AI 설계안에 있었던 'PM 유료 계획 생성 → 계약 동의' 순서는 기존 PRD·TF·ADR과 모순이므로 본 문서 및 원 설계안에서 **계약 동의 → PM 계획 생성 → 계획 승인 → 실행**으로 통일한다.

## 3. 도구/승인/재동의 게이트

| 행위 | 위험 | 기본 권한/승인 | 서버 차단 조건 |
|---|---|---|---|
| 프로젝트 문서 선택·결정적 비용 미리보기 | 사전 UI | owner, 무과금 | 인증 없음/타 프로젝트/삭제 |
| 해당 문서 스냅샷 읽기 | R0 | owner 계약+승인된 계획+실행 한도 | 다른 문서·새 버전/해지/승인 철회 |
| 별도 비공개 보고서 저장 | R1 | 활성 계약·owner 승인 계획 | 기존 문서 overwrite / 검증 안 된 외부 공개 |
| AI PM 유료 계획 생성 | 비용 발생 | 계약에 별도 budget/사용 목적 포함 | 초기 계약 미동의/예산 부족 |
| 원고/코드/프로젝트 DB 덮어쓰기 | R2 | **MVP 금지** | 어떤 AI 출력도 실행 요청으로 허가 불가 |
| 외부 발송·배포·결제·영구삭제 | R3 | **MVP 금지** | owner도 첫 계약에선 기능 불가 |

- **승인할 사람이 아닌 시스템이 승인 요청을 생성:** 서버 policy/approval service가 특정 run/task/도구·입력 대상 digest/리스크/비용/만료를 고정해 요청을 발행. PM은 요청을 *제안*할 수 있으나 DB 승인 행을 직접 생성·결정할 수 없음.
- **위임 없음이 기본:** editor 실행/수락/결제는 disabled. viewer/outsider의 알림/보고서 요약에 원문 노출도 차단.
- **재동의:** 계약 조건·document ID/digest·계획 버전·허용 도구·위험등급·공급자 처리 약관·원가 상한·만료가 변경되면 이전 승인을 재사용하지 않는다. 읽기 중 원본문서 변경은 이전 snapshot만 대상으로 검사하거나 실행 중단/재승인; 원문 자동 덮어쓰기 금지.
- **감사 정보 개념:** project_id, actor_id, contract_id/terms_version, task_id, plan_id/version, tool_key, risk, target_digest, approved_budget_minor/currency, expires_at, decision/decider, approval_digest, trace_id. SQL 컬럼 및 변경 정책은 P1-5에서 확정.

## 4. 비용 정책 — 공급자 원가, 고객 요금, 한도를 분리

| 구분 | 저장할 실제 사실 | 금지 |
|---|---|---|
| 공급자 **실비 원가** | model/tool/worker/스토리지별 estimate, reserved, observed, settled 또는 pending reconciliation | 고객이 수락 안 했다는 이유로 원가 0원 처리 |
| 고객 **청구/환불** | 상품·결제 계약이 최종 승인된 이후 별도 ledger | 내부 원가 추정치를 곧 고객 결제액으로 사용, 결제 실행 |
| owner **승인 예산 한도** | contract cap, plan-generation cap, run cap, active reserved, observed pending, settled | 동시 run이 상한을 초과하거나 불명확한 비용을 가용액으로 재사용 |

**서버 원장 설계 원칙:** 요청별 idempotency_key와 provider_ref 고유성, append-only event/상쇄 처리, DB row lock/compare-and-swap, 예약+run+outbox 원자성. 동일 공급자 청구 이벤트 두 번 수신 시 내부 장부는 한 번만 집계. 공급자 측 원 호출 과금 자체가 멱등하지 않을 수 있으므로 이중 과금 보장 표현 금지.

- **가용 예산:** 서로 중복되지 않게 계산한 확정 사용액 + 유효 예약액 + 미확정 공급자 채무액을 상한에서 보수적으로 차감. 미확정 제공자 사용량이 있으면 안전한 보류액을 유지; 표시된 '예상'과 '확정'을 섞지 않는다. 정확한 통화별/크레딧 공식은 P1-5 결정.
- **실패/재시도:** 자동 모델 재호출은 기본 OFF(횟수·예상 원가/총상한·공급자 중복 청구 방지 계약 없으면). 중복 HTTP 요청 재생은 같은 run만 반환하고 DB/도구/청구 중복을 방지. 별도 새 시도는 정책과 추가 비용 승인 후 진행.
- **지연 응답:** 공급자 실제 원가가 늦게 오면 pending reconciliation 유지. '0원'으로 확정하지 않고 예약 해제/정산은 대사 뒤 수행. 실패·취소 후에도 원가 발생 가능.
- **취소·계약 해지:** 미호출 예약은 해제 후보, 이미 발생한 공급자 비용은 실비 기록. 고객의 환불 자격/금액은 상품약관·법률검토 없이 단정하지 않는다. 실행/계약 해지 후 신규 도구 호출 즉시 차단, 진행 중 외부 호출의 취소 불가능성 고지.
- **무료 체험:** 얼마까지 무료인지, 카드/결제 등록을 요구할지, 비용 상한·공급자 약관 확인 전까지 숫자나 무제한 무료 약속 금지. 실제 외부 API 호출은 별도 권한/비용 승인 없으면 mock/fixture만 사용.
- **통화:** minor 정수, KRW=원, USD=센트. 통화/환율/크레딧은 다른 장부이며 상호 자동 상계 금지(환산 정책 별도).

## 5. 데이터 처리·보존/삭제 정책

- **실제 모델 전송 전 선행:** 공급자 및 모델별 목적, 국외 이전 가능성, API 입력·출력 학습 이용 여부, 저장·로그 보유기간/삭제 수단, 민감정보 마스킹, 계약·고지·동의 및 상업 이용 조건을 확인. 미확정이면 사용자 원문을 외부 모델로 보내지 않는다.
- **자료 최소 접근:** contract/approved plan에 등록된 document_id/revision_or_digest만 R0 도구가 읽고, 서버가 같은 프로젝트·owner·멤버십·문서 soft-delete·세션 검증. service_role RLS 우회 가능성은 별도 policy gate로 제한.
- **보존:** 보고서 최소 인용/locator·실행 메타데이터·사용량 증빙을 구별. 일반 로그에 원고 전체/비밀키/외부 자격 증명 저장 금지. 다운로드 URL은 시간·프로젝트·역할 제한.
- **미정:** 계약 해지 후 산출물·비용 원장·감사 이벤트의 보존기간, 민감 데이터 익명화/삭제·백업 파기 기간/국외 이전 고지. 미결정 시 '즉시 전체 데이터 완전 삭제' 또는 '사용자 데이터 안전 확정' 주장은 금지.
- **검증 분리:** schema 및 인용 위치 machine PASS는 문서 의미/사실 관계 human PASS와 같지 않음. generated/machine_verified/human_accepted 이벤트 분리.

## 6. 목표 상태·금지 전이(개념, 구현 아님)

| 범주 | 목표 상태 | 금지 |
|---|---|---|
| Contract | draft → accepted → active → suspended/expired/terminated | owner 동의·허용 도구·유효한 예산/데이터 조건 없는 active |
| PM plan | draft/generating → planned → approved / rejected / superseded | 계약/모델 비용 승인 전에 generating |
| Run | requested / awaiting_approval → queued → running → verifying → awaiting_acceptance → accepted/needs_revision/rejected; 예외 blocked/failed/cancelled | 검증 없이 accepted, 만료 계약으로 queued |
| Artifact | generated → source_verified / verification_failed → awaiting_human_review → human_accepted/rejected | '출처 존재'만으로 의미 정답/사용자 승인 주장 |
| Budget | estimate → reserved → observed/pending → settled/adjusted/released | 공급자 응답 없음 = 실제 비용 0원 |

상태/테이블 명칭은 구현 전 별도 SQL/OpenAPI 대상. 사람 승인 기록은 모델이 스스로 쓰지 않는다.
