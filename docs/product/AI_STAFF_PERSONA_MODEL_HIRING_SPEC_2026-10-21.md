# PlanOS AI 인력사무소 — 직무·캐릭터·경력표현·모델 라우팅·PM 운영 상세기획 v1.1

- **날짜:** 2026-10-21
- **상태:** 제품 상세설계 초안, 구현/실제 채용/실모델 연동 아님
- **상위 기준:** [사용자 제품 방향](DUAL_ENTRY_CONTINUOUS_AI_STAFFING_2026-10-21.md), [PRD](PRD.md), [기능정의서](FUNCTIONAL_SPEC_V1_2026-10-20.md)
- **핵심:** 직원은 단순 프롬프트/모델 별칭이 아니라 **직무(Job) × 대화·코칭 성향(Persona) × 숙련도(Tier) × 사용 모델(Model) × 권한·툴(Capability) × 고용·배정(Engagement)** 의 독립 조합이며, 사용자를 실제 프로젝트의 다음 행동과 산출물로 이끈다.

## A. 변하지 않는 제품 원칙

1. **기본 기획은 AI 기반:** 기존 PlanOS의 AI 인터뷰 → PRD 등 기존 산출물 생성 → AI 채팅 수정/재생성/사용자 편집은 그대로 제공. '직접 기획'은 사람이 수작업으로만 기획한다는 뜻이 아님.
2. **기본 직원 존재:** 역할별로 기본 제공 인력을 배치할 수 있고, 사용자는 직원 유형/직무/등급/모델을 선택해 교체·추가할 수 있음. 무료량/요금은 미정.
3. **실제 프로젝트 진행:** AI 직원은 친절한 채팅만 하지 않고, 맡은 직무의 계획·검토·수정안·테스트·근거 등을 프로젝트 업무/문서/승인함에 연결해야 함.
4. **고용 형태 구분:** 단발 의뢰 / 프로젝트 전담 / 선택한 복수 프로젝트의 전담 PM(정식 채용). 채용은 범위·기간·권한·비용 동의의 서비스 계약을 뜻함. 인간 고용 관계 아님.
5. **인격 vs 능력 분리:** 'F형/T형'은 제품의 의사소통 스타일 별칭이지 성격검사 점수나 전문성 인증이 아님. 공감형도 비판·결정하고 직설형도 모욕하지 않는다.
6. **경력 표시는 진실하게:** '대기업 PM 10년', '전 Google 개발자' 등 실제 경력처럼 위장 금지. 인물 배경은 **가상 설정**으로 명시; 숙련도는 내부 과제/평가에 근거한 **실행 역량 등급**으로 별도 표기. 평가/성능 실증 전 '시니어 인증' 사용 금지.
7. **실행 경계:** 기본 AI 기획/직원 선택/채용/PM 배정만으로 유료 모델 실행, 외부 전송, 코드 배포, 결제, 삭제, 최종 승인/수락 등의 포괄 허가가 생기지 않는다.

## B. 직원 카탈로그의 다차원 스키마

| 차원 | 사용자가 보는 선택 | 시스템 의미 | 독립 여부 |
|---|---|---|---|
| 직무 | PM/서비스기획/UX/리서치/디자인/프론트엔드/백엔드/풀스택/QA/콘텐츠/그로스/운영 | job_role + 업무 산출물/툴 계약 | 독립 |
| 소통 캐릭터 | 상냥한 공감형(F), 논리적 직설형(T), 차분한 분석형, 열정적 실행형, 창의적 발상형, 꼼꼼한 검증형 | persona_profile + feedback_policy | 독립 |
| 리딩 방식 | 함께 차근차근 / 방향 제시·승인받기 / 승인된 범위 내 위임 실행 | initiative_mode + approval_policy | 독립 |
| 등급 | 기본 / 중급 / 고급 (UI 가칭) | 테스트된 작업 범위·도구·품질·사용량·서비스 수준의 상품 묶음 | 독립 |
| 모델 | GPT 계열 / Claude 계열 / 향후 모델 공급자 | model_route(provider, model_id, version, capabilities, cost) | 독립 |
| 채용 형태 | 단발 업무 / 프로젝트 전담 / 복수 프로젝트 PM 정식 채용 | engagement_type / assignments | 독립 |
| 권한 | 보기 / 문서 초안 / 계획 수정 / 실행 제안 / 승인된 실행 / 외부 도구 | project-scoped permission + tool allowlist | 별도 사용자 승인 |

**중요:** UI에서 '고급=Claude', 'T형=GPT'처럼 고정 매핑하지 말 것. 실제 모델·툴 호환/성능 검증을 통해 직원마다 기본 모델을 추천하되 가용성/권한/요금 조건 안에서 교체 가능하도록 설계.

## C. 캐릭터·직원 예시 (전부 서비스용 가상 인물 콘셉트, 실제 구현된 AI 아님)

| 표시명 | 직무 | 성향·지도 방식 | 단계/모델 후보 | 사용자를 이끄는 행동 | 산출물 |
|---|---|---|---|---|---|
| 하루 | PM | F형 공감·질문·작은 실행 강조 | 고급 콘셉트 / GPT 계열 후보 | 불안한 사용자의 목표·막힘 이해 → 오늘 1~3개 실행 항목 제시 → 체크인 | 주간 계획/진척 요약 |
| 태오 | PM | T형 팩트·우선순위·날카로운 건설적 피드백 | 고급 콘셉트 / Claude 계열 후보 | 잘못된 가정 지적 → 검증 실험 제안 → 완료기준·기한 제시 | 위험 분석/업무 분해 |
| 로이 | 풀스택 | 분석형·구현 중심 | 중급/고급 평가 전 / 모델 비교 | 저장소/기술 계약 확인 → 작은 코드 변경 → 테스트 → PR 요청 | 코드 diff/검증 로그 |
| 소담 | UX·서비스기획 | 공감형·사용자 관찰 중심 | 중급 평가 전 / 모델 비교 | 사용자 문제 정리 → IA/화면 흐름 → 빠른 검증 | IA/스토리보드 |
| 린 | QA | 세밀한 검증형·반례 중심 | 중급 평가 전 / 모델 비교 | 수용기준을 테스트 사례로 변환 → 실패 증빙 수집 | 결함 보고서 |
| 제이 | 그로스/마케팅 | 실험형·실행 촉진 | 기본/중급 평가 전 / 모델 비교 | 타깃·메시지 → 작은 실험 → 성과 대조 | 실험계획/지표 |

직원의 캐릭터 문구 예시:
- 하루: “막막하신 건 이해해요. 오늘은 첫 고객이 왜 필요한지만 분명히 하고, 한 가지만 끝내볼까요?”
- 태오: “현재 자료만으로는 유료 전환 근거가 부족합니다. 기능 추가보다 고객 인터뷰 3건을 먼저 실행하죠.”
- 로이: “배포 전에 저장/권한 회귀가 필요합니다. 변경 파일·통과 로그·미검증 항목을 나눠 보여드리겠습니다.”

'상냥한 F'는 무조건 동의하지 않고, '팩폭 T'는 공격/비난하지 않음. **업무 기준·판단/근거는 성격에 따라 달라지지 않고 전달/코칭 방식만 달라짐.**

## D. 상세 직원 프로필 UI (고용을 결정하는 정보)

1. 상단: 아바타, 가상 이름, 직무, 전문 분야, 소통 스타일 칩, 리딩 성향.
2. 능력: 할 수 있는 일 3~5개, 하지 못하는 일, 실제 연결 가능한 도구/데이터와 지원 기술 스택.
3. 성능 근거: 테스트 작업/완료된 검증 시나리오/실패율/검토 일자. 수치가 없으면 '아직 검증 전' 표기.
4. 모델 정보: 제공자(OpenAI/Anthropic 등), 실제 선택된 model_id, 모델 변경 여부, 호환 기능/비용/한계. 모델명에 직원 정체성을 종속하지 않음.
5. 소통 미리보기: **같은 업무**를 공감형/직설형이 어떻게 피드백하는지 2~3턴 비교. 성향 조절 옵션(따뜻함, 직설성, 질문 빈도, 세부 설명 정도).
6. 채용 UI: **일회성 업무 맡기기** / **프로젝트 전담 채용** / **PM 정식 채용(복수 프로젝트)**. 사용량·가격 정책이 정해지기 전 결제 활성화 금지.
7. 계약 카드: 프로젝트·문서 범위, 쓰기/실행 권한, 기간, 제안/승인 한도, 예상/상한 비용, 개인정보·외부 전송 고지, 해임/교체의 영향.
8. 활동/이력: 결과물 증거, 작업 상태, 승인 요청, 모델 라우팅 감사 기록, 책임 분리.

## E. PM 정식 채용의 실제 사용자 경험 (제품의 가장 중요한 기능)

**예시:** 사용자가 태오 PM을 정식 채용하고 'PlanOS, 개인 포트폴리오, 전자책 도구' 3개 프로젝트를 선택한다.

- **채용 시:** 담당 프로젝트 체크박스(현재 3개만), 읽기/계획/업무 생성/협업 요청 권한, 업무 실행 승인 방식, 예산/계약 기간 확정. 이후 신규 프로젝트 자동 추가는 기본 OFF.
- **첫 점검:** PM이 각 프로젝트의 최신 저장 문서와 업무 상태를 확인하여 목표·막힌 일·다음 마일스톤을 보여 준다. 미저장/접근 불가 자료는 확인 필요로 표시.
- **실제 리딩:** “A는 고객 검증부터, B는 포트폴리오 화면 검수, C는 저장 오류 테스트를 우선하세요”처럼 프로젝트별 오늘의 실천 제안을 제시한다.
- **일 분배:** 허용된 범위에서 QA/개발 직원에게 업무 초안을 만들어 전달한다. 다른 직원을 고용/비용 집행하는 행동은 승인 요청. 상태는 사람 업무/AI 실행/산출물 수락으로 분리한다.
- **중간 개입:** 사용자가 기존 AI 기획 인터뷰와 채팅을 직접 계속 쓰거나, PM 피드백 스타일을 바꾸거나, 특정 프로젝트 담당을 제거할 수 있다.
- **주기 진행:** 실제 자동 체크인/알림이 가능하려면 서버 scheduler+worker+권한/예산 재검증+실행 로그가 있어야 함. 화면만 만들어 놓고 백그라운드 운영한다고 표시하지 않는다.
- **교체:** 하루 PM으로 교체 시 기존 프로젝트·업무·산출물·로그와 승인 이력을 그대로 두고 현재 작업을 안전하게 일시 정지, 새로운 PM의 배정 범위/초기 브리핑을 다시 확인.
- **해임:** 이후 새 AI 작업 예약 중지, 접근권한 철회, 이미 생성된 기록 보존·진행 중 청구/작업 정산 안내.

**PM의 핵심 성과:** '말을 잘함'이 아니라 *목표가 작업으로 바뀌고 실제 검토 가능한 결과가 생기는가*. 프로젝트별 제안 수용·완료·재작업과 사용자 개입량 측정.

## G. 기술 구조: Employee ≠ Model ≠ Run

필요한 논리 객체(테이블/컬럼 이름은 **설계 제안**, 실제 DB migration 아님):

| 객체 | 필수 데이터 | 일관성/보안 |
|---|---|---|
| staff_archetype | archetype_id, job_role, persona_version, display_name, synthetic_bio, capability_ids | 가상 설정 명시; 원본/변경 이력 |
| capability_evaluation | capability_id, task_type, tested_model, eval_date, outcomes, limitations | 검증 성능/등급의 출처 |
| model_registry | provider, model_id, context/tool_capabilities, pricing_ref, enabled, last_verified | 이름/도구/가용성 동적 검증·버전 기록 |
| staff_configuration | archetype_id, persona_override, job_capability_profile, model_route_id, tier | 성격/역할/모델/등급 독립 |
| staff_engagement | hire_id, owner_user_id, status, engagement_type, budget/contract versions | 단발/지속 채용·취소/만료 구분 |
| staff_project_assignment | hire_id, project_id, permissions, assigned_at, revoked_at | 다대다 명시적 배정, RLS 경계 |
| staff_task/run | hire_id, project_id, task_id, source_revision/digest, approval_ref, provider/model_id, idempotency_key, status, cost | 과금/실행/문서 버전 원자성·재시도 |
| staff_activity | actor, project_id, action, evidence, timestamp, status | 실제 행동 vs 제안/모의 구분 |

**호출 파이프라인:** 프로젝트 권한 확인 → 업무 타입/직무/도구 허용 확인 → 채용·배정·예산·전송 동의·자료 digest 검증 → 선택 모델 라우팅 → 구조화 tool call → 서비스 서버가 실제 권한으로 실행 → 결과/evidence 저장 → 인간 검수 및 PM 브리핑.

OpenAI·Anthropic은 각각 도구 호출 인터페이스를 제공하지만, **실제 함수 실행/권한 검증/외부 데이터 접근은 PlanOS 서버가 책임**. 공급자 어댑터를 분리하고 모델마다 호환 가능 기능과 프롬프트/구조화 응답 검증을 둔다. **모델 변경/장애 시 자동 타 공급자 전송 금지**: 사용자가 고른 공급자와 데이터 전송 범위에 따라 다시 동의/확인. 미확정 모델 버전·가격을 문서에 고정 기재하지 않는다.

## H. 성격 엔진과 품질 가드

- **변경 가능한 영역:** 높임말/유머/공감 표현, 직설성, 피드백 길이, 질문 빈도, 사용자를 독려하는 방식, 답변 형식.
- **변경 불가 영역:** 사실 확인, 틀린 기획 지적, 데이터/직원/모델 출처의 정직한 표시, 근거/버전/권한/비용, 편집 충돌 보호.
- **PM 행동 계약:** 모든 답변/주도 브리핑에 '현재 파악한 상태 → 판단 근거 → 우선순위/다음 행동 → 필요한 승인·차단 사유'가 구분되어야 함. 진행을 못 했으면 못 했다고 표시.
- **사용자 설정:** 직원 성향 선택 이후에도 '조금 더 직설적으로', '덜 재촉하기', '상세하게 안내' 등의 조정 가능. 기존 업무 컨텍스트는 유지하고 프롬프트 버전 변경은 기록.
- **과업 내 모델 평가:** 성격 평가와 산출물 품질 평가를 분리; 친절한 직원과 직설 직원의 공통 테스트에서 동일한 필수 사실·수용기준을 만족해야 함.

## I. MVP 개발 우선순위와 기능 게이트

| 순서 | 기능 | 실제 검증 조건 |
|---|---|---|
| 0 | G1 저장·복원·RLS P0 (별도 병행) | 기존 자동저장/복원/채팅 원자성·권한·E2E |
| 1 | 직원 프로필·성향 선택 **Mock** | 같은 업무에 다른 스타일 답변 비교, 검증 전/가상 경력 표시, 모델 호출 없음 |
| 2 | 기본 직원 ↔ 다른 직원 교체·단발 의뢰 **Mock** | 역할·성향·모델 독립, 같은 문서/프로젝트 ID 유지, 미지원 기능 고지 |
| 3 | 정식 PM 채용·1개/복수 프로젝트 배정 **Mock** | 선택하지 않은 프로젝트 접근 거부, 변경·철회/세션 E2E |
| 4 | PM 계획/브리핑 실질 업무 연결 | 기존 AI 인터뷰·문서/업무 상태 참조; 상태·일정·근거 기반 요약; 승인함 |
| 5 | 모델 레지스트리/다중 공급자 서버 어댑터 | 기능/가격/권한/전송 계약 검증 후 제한 호출, model_id별 증빙 |
| 6 | 스케줄러·실제 실행·전문가 위임/비용·통합 QA | 작업 큐·실행 수락·취소/재시도·청구/권한·복구 E2E |

### 1차 MVP 권고
- 직무 3개(PM, 풀스택, QA) + 소통 성향 2개(공감형/직설형)로 **6개의 조합**부터 검증. 직원의 실체를 6개 별도 백엔드로 중복 구현하지 않고 역할/성격 설정 조합으로 제작.
- 중급/고급은 실제 품질·도구/비용 차이가 실증되기 전까지 **모의 비교**만 제공. 고객 대상 허위 고급 등급 판매 금지.
- 정식 PM은 처음에 **선택 1~3개 프로젝트를 묶는 배정/브리핑 흐름**으로 검증하되, 향후 복수 확장 가능한 DB 구조는 초기부터 설계.
- 이전 Mock PR #25(단발 AI 검수)와 #27(사람 PM 계획)은 활용 가능하지만 **정식 AI 직원 채용이나 실제 PM 다중 프로젝트 운영이 이미 구현됐다는 근거가 아님**.

## J. 테스트/수락 기준

- **ST-01** 기존 AI 인터뷰·5종 산출물·채팅 수정 경로 손상 없음.
- **ST-02** 동일 업무에 F/T 성향 적용 시 말투는 달라도 사실·수용조건 일치.
- **ST-03** 모델 교체 후 provider/model_id·비용·도구 기록 정확. 미동의 공급자 자동 우회 없음.
- **ST-04** PM vs 풀스택/QA 역할 간 작업 가능 범위·도구 권한 차단 검증.
- **ST-05** 기본 직원 교체, 업무 중단·재배정 시 이력·사용자 편집 및 문서 버전 보존.
- **ST-06** 일회성 의뢰와 정식 채용의 유지기간/업무권한/과금 경계.
- **ST-07** PM에 A/B 배정 후 C 열람·수정/요약 불가. 여러 프로젝트 통합 뷰에서 데이터 섞이지 않음.
- **ST-08** PM 해임/만료 즉시 새 실행 차단 및 미확인 상태/비용 정산.
- **ST-09** 미승인 실모델 실행/배포/외부 전송·자동 신규 프로젝트 접근이 발생하지 않음.
- **ST-10** 실행 중 문서 수정·채팅 재생성·복원 시 stale snapshot/계약·계획 처리.
- **ST-11** PM 자동 체크인은 실제 서버 job 성공 시에만 수행했다고 표기.
- **ST-12** 친절형과 직설형 모두 프로젝트를 다음 검토 가능한 결과물로 진전시키는지 실제 사용자 평가.

## K. 현재 상태와 의사결정 미완료

- 제품 구조와 예시 직원 이름/성향/모델 배치는 **제안**이다. 실사용 경력, 특정 모델의 직무 적합성, 가격/성능, 유료/무료 제공 조건은 아직 확정된 사실이 아니다.
- 직원 실제 서비스에 필요한 모델 공급자 계약, API 비용, 국외 전송, 프롬프트/데이터 보존 정책, 도구 범위, 평가 기준, 자율 실행/해임의 동작은 구현·검증 후 확정한다.
- 다음 작성 문서: 화면별 스토리보드·상태 전이·권한 매트릭스·데이터/API 상세 계약. 설계 완료만으로 기존 G1~G7 릴리스/병합 게이트를 해제하지 않는다.
