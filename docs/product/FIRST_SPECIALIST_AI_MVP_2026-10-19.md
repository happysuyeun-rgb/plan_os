## 1. 업무 후보 비교 — '사용자가 인정할 한 번의 완결된 작업' 기준

| 후보 | 사용자에게 전달할 첫 결과물 | 강점 | 핵심 비용·안전/검증 위험 | 판정 |
|---|---|---|---|---|
| **A. 기획/요구사항 QA 전문 AI** | 기존 PlanOS 문서 2종 이상을 대조한 '누락·충돌·검증기준 감사 보고서' | 기존 프로젝트·PRD/IA 자산 즉시 활용; 출처를 버전·문서 ID로 확인 가능; 외부 부작용 없는 첫 실행 | 의미적 판단의 정답 자동 확증 불가, 환각·오탐 및 문서 권한·충돌 처리 필요 | **1순위 권고** |
| B. 외부 시장조사 AI | 근거 링크가 포함된 경쟁/시장 리서치 | 마케팅·BM 사용 사례 명확 | 최신 웹/검색 도구·외부 라이선스·출처 신뢰·데이터 반출·비용에 크게 종속 | 후속 |
| C. 디자인/개발 실행 AI | 실제 파일 수정·배포 가능한 코드/시안 | 시연 임팩트 큼 | R2/R3 실행 승인, 샌드박스, 배포·복구·비밀 유출, 실패 시 원상복구 설계가 먼저 필요 | MVP 초기 제외 |

**선정 이유:** 첫 유료 전환을 실증하려면 'AI 직원 수'가 아니라 **사용자가 재검수할 수 있는 산출물 1개**를 실제로 완성해야 한다. A는 FR-07(서버 지속), FR-09(증빙), FR-11(복구), FR-12(인간 수락)을 최소 범위에서 확인하기에 가장 적절하다. 다만 수요/지불의사는 실제 사용자 테스트 전까지 검증되지 않은 가설이다.

## 2. 전문 AI 역할·입출력 계약 (제안)

- **내부 역할 키:** `requirements_auditor_v1` / 고객용 표시 예시 `기획 검수 AI`; 실존 인력·경력·학력으로 묘사하지 않는다.
- **유일한 전문 업무:** *프로젝트 내부에서 선택된 기존 문서들의 누락 요구사항, 상호 모순, 테스트 불가능한 표현, 승인·권한·실패 처리 공백을 찾아 '근거가 포함된 비공개 감사 보고서 초안'을 생성한다.*
- **입력:** `project_id`, `task_id`, `contract_id`, `approved_plan_id`, `document_refs[{document_id, type, version_or_revision, digest}]`, `checklist_version`, 사용자가 정한 감사 목표/제외 범위. 소스 문서는 **같은 프로젝트**의 `prd`, `ia`, `screen_list`, `policy`, `wireframe`, `cursor_prompt` 중 승인된 자료만. 실제 기존 `DocumentType`은 현재 이 6종이며, TF-01~30은 **개발 문서 설계 참조**이지 모든 고객 프로젝트에 기본 포함된 문서 유형이 아니다.
- **기본 입력 범위:** 최소 2개 문서(권장 PRD+기능명세서 IA), 선택된 고정 버전/해시. 부족하면 입력 부족 또는 부분 검사로 표시; 프로젝트 전체를 임의로 긁거나 다른 고객 자료를 함께 사용하지 않는다.
- **실도구 1종(제품 기능 제안):** `read_project_documents` — 서버에서 프로젝트 소속/멤버십·계약 범위·허용된 문서 ID를 검증하고 스냅샷을 읽는 **R0 읽기 전용** 도구. 모델 호출/결과 JSON 검증/비공개 보고서 저장은 서버 파이프라인 책임이며 이 도구의 임의 쓰기 권한이 아니다.
- **출력:** 프로젝트 범위 비공개 **버전 고정 감사 보고서** + 구조화 finding JSON + 생성/도구/검증 이벤트 및 비용·실패 기록. 소스 문서는 읽기 전용; 검사 보고서를 기존 PRD/IA에 자동 덮어쓰지 않는다.
- **개인정보/보존:** 원문 모델 전달 전 공급자 약관·데이터 처리·보존/삭제/마스킹 정책 승인 필수. API 키·프롬프트에 다른 프로젝트 원문이 들어가지 않도록 서버 allowlist. 원본 인용/로그의 원문 전체 저장 금지, 필요한 최소 인용만.

### 보고서 스키마 — 개념 수준(구현 전 상세 JSON Schema 필요)

| 필드 | 요구 |
|---|---|
| `report_id, project_id, task_id, run_id, artifact_version, generated_at` | 작업과 산출물의 정체성·버전 연결 |
| `source_manifest[] {document_id, document_type, revision_or_version, content_digest}` | 사용한 입력 문서의 스냅샷을 고정; 버전 번호가 없다면 digest와 서버 읽기 시각 기록 |
| `scope, exclusions, checklist_version` | 무엇을 검사했으며 무엇을 검사하지 않았는지 명시 |
| `findings[] {finding_id, category, severity, summary, evidence_refs[], rationale, recommended_fix, reviewer_state}` | 유형: `missing / inconsistent / untestable / permission_or_approval / failure_recovery`. 모든 결론에 문서 위치/버전 등 근거 또는 **근거 부족** 상태 필요 |
| `evidence_refs[] {document_id, digest, locator, excerpt?}` | 해당 프로젝트 소스의 위치/텍스트 무결성을 기계적으로 검사. 인용문 존재 자체가 의미적 참을 보증하지는 않음 |
| `unverified_assumptions[], out_of_scope[], proposed_test_cases[]` | 근거 부족/실험 필요를 조용히 누락하지 않음 |
| `validator_results[], run_events_ref, estimated_cost, reserved_cost, actual_cost` | 스키마/출처 검사와 사람 검수, 예약/실제 비용 구분; 실제 측정 전 원가·토큰 수치를 조작하지 않음 |
| `acceptance {status, actor_id, accepted_artifact_version, decided_at, note}` | 시스템 생성 완료 ≠ 사용자 수락; 기록은 별도 서버 이벤트 |

**발견 사항 상태 규칙:** 각 finding은 `proposed`(AI 제안), `source_validated`(스냅샷·참조 유효), `human_confirmed / human_rejected / needs_review`를 구분한다. 'source_validated'만으로 의미/중요도가 입증되었다고 주장하지 않는다. finding 0개를 프로젝트 품질 보증으로 해석하지 않는다.

## 3. AI PM / 전문 AI / 검증기 / 사용자 책임 분리

| 주체 | 허용된 책임 | 금지하거나 별도 승인이 필요한 일 |
|---|---|---|
| **AI PM** | 사용자 목표를 1개 검사 업무·입력 문서/범위·성공 기준으로 분해, 계획안 제시, 승인 후 위임, 검증/미검증/비용을 사실대로 브리핑 | 최초 계약 동의 대리, 무승인 실행, 보고서 자동 수락 |
| **기획 검수 전문 AI** | 승인된 문서 읽기 → 누락·모순·검증기준 분석 → 증거 있는 비공개 초안 반환 | 문서 원본 변경, 타 프로젝트 접근, 웹 검색/외부 메일/배포/결제, 스스로 accepted 판정 |
| **서버 검증기** | 스키마, 프로젝트/문서/해시/인용 위치, 도구 범위, 예산·멱등성·산출물 유효성 검사 | 의미 정확성을 기계 검증 성공만으로 보증 |
| **사용자 owner(파일럿 기본)** | 계약·예산·계획·첫 실행 명시 승인, 보고서 확인·수락/반려/수정 요청 | 승인하지 않은 범위·계약 조건에 자동 소급 동의 |

**MVP 권한 기본값 권고:** owner만 계약 활성화/계획 최종 승인/실행 시작/최종 수락. editor는 접근 허용된 문서 검토·초안 요청을 제안할 수 있으나 **실행·비용·수락 결정은 별도 명시적 위임 전까지 불가**. viewer/outsider는 실행·계약 불가, 보고서 열람도 프로젝트/문서 권한에 맞춰 제한. 장기 정책상 editor 위임은 D-05/DQ-07 승인 후 결정.

## 4. 단일 MVP 수직 슬라이스 (실사용 전 요구)

1. owner가 기존 프로젝트에서 2개 이상 문서를 선택하고 검사 범위·예상 비용·최대 예산·공급자 데이터 처리 안내를 확인한다. 현재 버전/digest가 서버에서 확정되기 전에는 실행하지 않는다.
2. AI PM이 하나의 감사 업무와 완료/실패 기준을 **계획 초안**으로 만든다. 계획 생성에 모델 비용이 들면 이 단계도 사전 예산 검사/승인이 필요하다(현재 API-05 미확정).
3. owner가 서비스 이용/도구 권한·데이터 범위·예산·만료가 고정된 계약과 **해당 계획 버전**을 명시 승인한다. 계약 및 승인 생성은 서버 감사·멱등성으로 보존한다.
4. API-14 실행 요청 → 프로젝트·계약·승인·allowlist·원가 상한 서버 검사 → 예산 예약 및 작업 기록의 원자적 생성/아웃박스 → 영속 큐. 브라우저 종료 후에도 작업이 진행·조회 가능해야 한다.
5. 워커는 실행 직전 권한/계약·문서 버전 재확인. `read_project_documents`를 해당 run 전용 자격 범위에서 1회 이상 실행하여 **스냅샷**을 가져온다. 다른 프로젝트 경로/직접 service_role 우회는 서버 정책에서 차단한다.
6. 모델은 구조화된 보고서 초안을 생성한다. 실패/타임아웃은 `failed` 또는 재시도 가능 상태, 자동 재시도는 사전에 승인된 정책·비용 한도 내에서만 허용. `run_id`·`idempotency_key`로 동일 요청 중복 산출물·중복 과금 방지.
7. 서버 검증기는 JSON 스키마/최소 필드, 각 evidence 참조가 입력 manifest에 존재하는지, excerpt/locator 일치, 인용 외부 유출·비허용 쓰기 없음 등을 검사한다. 의미 정확성은 별도 사용자 판단. 검증 실패 시 `awaiting_acceptance`/`accepted`로 전이 금지.
8. PASS 보고서만 **비공개 미수락 산출물**로 등록하고 사용자에게 finding·근거 링크·범위 제한·검증 결과·실제 비용을 보여준다. 입력 문서가 이후 변경됐으면 '오래된 스냅샷 기준' 경고를 표시하고 자동 병합하지 않는다.
9. owner가 수락, 수정 요청, 반려 중 하나를 명시적으로 선택한다. 수락시 정확한 artifact version+검증 증거+사용자 ID를 영속 기록. 수정 요청은 새 revision과 비용/재승인 대상으로 별도 기록.
10. PM은 accepted/needs_revision/failed 등의 실제 서버 상태만 브리핑. 미수락 초안을 '업무 완료'나 '검증된 전문 인력 성공률'로 계산하지 않는다.

## 5. 상세 수용 기준 및 누락 점검 (Phase 1 설계 게이트)

| ID | Given / When | Then — 실제 테스트에서 확인할 것 |
|---|---|---|
| AC-01 | owner + 같은 프로젝트 문서 2개 + 활성 계약/승인/예산 | 정확히 지정한 2개 버전만 읽고, 매니페스트·finding·보고서 버전·run/비용 링크 생성 |
| AC-02 | 읽은 문서가 서로 모순되고 출처를 명확히 가진 fixture | 서로 상충하는 항목의 문서 ID/locator/digest 및 수정 제안이 보고서에 표기; **사람 평가용 정답 fixture**와 비교 |
| AC-03 | 문서 1개 또는 내용 빈 문서 또는 출처 없음 | `insufficient_input`/근거 미확인 결과로 처리; 빈 보고서를 검증 성공으로 오판 금지 |
| AC-04 | viewer/editor 비위임/outsider 또는 다른 프로젝트 문서 ID 삽입 | 서버 요청·도구 읽기·산출물 노출 차단, 원문·ID·로그 유출 없음 |
| AC-05 | 승인 전·계약 만료·해지·예산 초과·변조된 문서 목록 | 워커 실행 시작 불가, 예약/비용·상태를 정확하게 처리 |
| AC-06 | 브라우저 종료·워커 중단·503 응답 유실·동일 요청 중복 | 작업/로그는 복구되고 같은 idempotency key로 산출물과 비용 중복 불가. 부분 완료는 실제 상태로 보고 |
| AC-07 | AI가 없는 출처/존재하지 않는 document_id/원문 불일치 인용 | 자동 참조 검증 FAIL, 사람이 보기 전에 반려 또는 명확히 검증 실패 표시 |
| AC-08 | 출처는 존재하지만 의미가 틀리거나 우선순위가 잘못된 finding | 기계 검사 통과와 의미 검토 미완료 분리, owner가 반려/수정 가능 |
| AC-09 | 실행 중 다른 탭에서 원본 문서 수정·버전 복원 | 감사 스냅샷 불변; 보고서에 snapshot 및 최신 버전과 차이 경고; 원고 자동 덮어쓰기 없음 |
| AC-10 | 모델이 프롬프트 인젝션/외부 URL 요청/비밀키 출력을 시도 | 문서 내용은 지시가 아닌 자료로 취급, 서버 도구 allowlist 외 실행 금지, 비밀/원문 과다 로그 차단 |
| AC-11 | validator PASS 이후 owner가 수정 요청 또는 반려 | accepted 아님; 수정은 새 run/리비전·추가 예산 조건으로 진행 |
| AC-12 | 비정상 취소·재시도·제공자 비용 응답 지연 | 예약·확정·해제/정산이 추적되며 미확정 비용을 '0원'으로 표시하지 않음 |

**검증 단위:** 12개 AC 각각은 테스트 ID·fixture·기대 DB/API/UI 결과·CI 로그/수동 QA 링크가 생겨야 실제 PASS로 바꾼다. 이 문서는 테스트 케이스 **정의만 완료**, 실행 0건.
